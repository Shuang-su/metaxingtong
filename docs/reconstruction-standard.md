# 直播3D场景重建：完整需求与交付门槛

确认日期：2026-10-10。按用户本次明确要求记录；适用于既有场景续作与后续新增场景。所有历史冻结版本保留，后续纠正另作新阶段。

## 1. 识别直播场景与有效内容

- 直播间是可运镜的3D空间。尽量完整检查每部相关回放，利用不同运镜理解同一场景的空间；记录实际检查的时间范围和未检部分，不以少数抽帧冒称完整看完。
- 跳过无实际空间信息的片头、CG、混剪等无关片段。评论中的数字可作为定位正片的线索，跳转后必须核验实际内容，评论本身不作空间结构证据。
- 同一视频可能有多个场景，也可能是一个大场景的不同部分。依据连续运镜、共享固定物、连接关系和布局分别识别；未证连通不强行拼接，多场景分开管理。
- 每场记录所属直播场次、可核实标题/日期、BV号与链接、片内时间和场景身份。日期或场景关系未知就明确写未知。

## 2. 登录后的高清来源与新增多角度

- 必须登录后选择该视频在当前账号权限下可用的最高画质播放和截图，并补回此前回放的高清参考。视频支持且当前会话可实际解码4K时，使用原生4K；1080P不再作为固定上限。记录每张来源的实际片内时间、登录/画质证据、解码尺寸、截图尺寸、有效裁图范围；菜单列有某画质不等于该画质已实际解码。
- 后续视频中的新增多角度也必须用于确认，并先验证是否同一场景；记录搜索/检查过的回放及时间范围。没有找到有效新角度时记录已检范围与缺口，不能将“没找到”写成通过。
- 同一视频较晚时刻，不等同于“后续其他回放”；同轴缩放、同机位季节切换、重复构图、转场混合帧不计作独立空间基线。
- 解码视口截图与原生导出帧分别标注实际尺寸和取得方法（包括1080P、4K等），不能混称；优先按第10节用浏览器自带“将视频帧另存为…”保存PNG。高清补采必须进入当前改模和最终叠图证据链，仅有文件不代表已经用于验证。

## 3. 空间理解、白模与纹理

- 先据真实多角度建立共享白模，再创建对应纹理贴图和材质，逐物件还原。
- 区分实体、孔洞、玻璃、材质明暗和光影制造的阴影，不能把阴影造型误建为实体，或拿黑色条纹替代真正镂空结构。
- 室内必须补为有限、完整、几何完备的房间：墙/地/顶相接，保留真实门窗开口、厚度、进深、回边、支撑、落地与通行净空。
- 原本开放的露台、花园、海滨、舞台等保持其开放性质；不要为“闭合”强行封口或扩成未知整栋建筑。
- 隐藏背面、未知相邻房间、尺度和支撑做法均明确标为推定，不能冒充来源观察或实测尺度。

## 4. 同机位对照并持续改进

- 将模型置于与每张参考图相同的相机角度，保留来源图、渲染图和直接50%叠图，对照实际差异后改进。
- 所有来源机位共用同一套几何、材质和照明状态；不得按镜头隐藏墙、变形物件、局部扭曲叠图来制造一致。
- 内部几何检查视角不能充作来源角度；另给至少8个任意方位检查图，剖切、俯视和诊断补光明确标注。
- 最终输出一张主视角图片供用户确认，连同可编辑材质模型、同几何白模、纹理/检查资料和跨软件导出；图片交付不等于用户接受。

## 5. 分开的验收门槛

- 几何：实体厚度、法线、接触与接缝、开口允许域、密集射线、通行与支撑，及真实GLB重新导入核验。
- 来源：登录后高清引用链、后续回放的同场新角度、共同空间解释、相机对齐、物件数量/遮挡/比例、材质与照明残差。
- 交付：模型/贴图/白模一致性、主视角图、清楚的未完成项和用户确认状态。
- 几何检查通过或文件可打开都不能代替来源还原通过。任何必需来源门槛未证实，状态保持“重建候选 / 待来源复核”；未收到用户验收，不写已接受。

## 6. GitHub逐场完整历史

- 私有仓库内每场独立Issue、阶段评论、真实commit与Draft PR，参照Metaflow的目标、范围、spec/plan/report、证据与限制记录方式。
- 从最早可核实版本的改动开始详细补录。保留真实旧包、版本变化、失败/撤回方案、来源链接与原始事件日期；缺失版本只记缺口，不伪造模型、旧发布或旧commit。
- 所有本次commit/Issue评论使用真实创建时间。Library附件版本与场景V编号分开，Library创建/修改时刻不自动等于聊天发送时刻。

## 8. 逐物件拆分确认（2026-10-11用户新增）

整场重建必须建立逐物件核验表，不能只以整张主图“大致相似”代替物件确认。

1. **身份与实例定位**：为每种物件和每个重复实例分配稳定ID，记录所在场景、相对位置及朝向。重复桌、椅、灯、柱、窗等必须说明是哪一个实例，依据位置/邻接/连续运动对应，不能将近似重复件混配。
2. **来源证据**：逐件记录所属直播场次、BV链接、实际片内时刻、原生或视口尺寸、所见视角和遮挡。区分真实来源、同角度渲染、局部裁切、叠图及结构诊断。裁切或放大同一张图不会增加来源机位数量。
3. **逐项确认**：检查轮廓、比例、厚度、进深、支撑与接触、孔洞、朝向、遮挡关系、材质及照明。明确区分实体边、玻璃/透明、纹理、反射和阴影；不得由单条明暗分界直接确认实体造型。
4. **同视角局部对比**：保留原图及其明确坐标裁切，使用同一来源相机条件下的物件局部渲染/直接叠图检查。记录原始像素、裁切区域与任何显示缩放；不warp或局部变形来掩盖残差。未完成相机标定的比较明确标为条件性诊断。
5. **结论分级**：每个属性分别标“来源证实”“推断”“待查/未见”，附依据与残差。看不见的背面、脚、支撑、尺寸和材质不能强称确认；尺寸没有真实尺度依据时用模型单位。
6. **隔离展示边界**：拆开或单独展示物件仅用于结构/材质诊断，必须标注隔离或剖切。不能通过渲染时隐藏其他物体、修改遮挡或按机位开关物件来伪造全场来源叠图。
7. **回到共同场景**：单物件候选必须放回同一套共享几何、材质和状态，回归全部已使用来源机位和任意检查视角，检查接触、尺度、遮挡及对其他物件的连带影响。局部改善不能代替整场回归；失败候选与后续勘误保留。
8. **显式状态区别**：有可靠时间证据的布置状态与动态角色可独立记录；同一明确状态内各相机仍必须一致。状态选择不能偷偷绑定相机，未知时间不外推为已知。

逐物件检查通过也不能单独把整场标为来源已验收。未确认项目应成为后续补源/改模任务，并在所属Issue呈现对应图证。

## 10. 原生视频导帧流程（2026-10-11用户确认；2026-10-13补充最高画质与菜单操作）

### 10.1 获取真实解码帧

1. 登录来源平台，确认正确直播场次、BV/视频链接和场景。选择该视频在当前登录账号下实际可用的最高画质，并等待播放切换和解码稳定；支持且可实际解码4K时使用原生4K，不以1080P封顶。分别记录请求的画质档位、实际生效档位和真实videoWidth/videoHeight；画质菜单选项、会员标识或网页窗口大小不能替代解码核验。避开无关片头、CG混剪及叙事背景。通过连续播放辨认同场、相机运动和布置状态，评论区时间标记仅作寻找线索。
2. 定位参考附近时刻，暂停并等待帧就绪。记录保存前与保存后的 `currentTime`、`paused`、`readyState`、`videoWidth/videoHeight`；本批可复验条件是两次均paused=true、readyState=4、currentTime相同且解码尺寸相同。记录实际值；不把未达到条件的帧假填为通过。
3. 优先使用浏览器自带的原生视频菜单“将视频帧另存为…”保存PNG。在B站云浏览器中已复现的入口操作是：正常右键先出现B站自定义菜单，再在未被菜单遮住的视频区域右键。浏览器原生菜单可能是独立弹出窗口，单独浏览器窗口截图会漏掉；应查看全桌面截图，确认“将视频帧另存为…”入口。本次云端复测中，选中保存项后将鼠标移入该项，再按Enter，可稳定触发下载；仍须核验实际下载文件。此方法无需安装扩展或修改chrome://设置。菜单入口出现只证明可以尝试保存，不等于PNG已经取得或核验通过。保留下载原字节，不通过放大网页窗口、截图插值、重采样或AI补图凑1080P、4K等目标尺寸，不通过脚本绕过来源站点访问限制。
4. 独立读取导出PNG的IHDR并实际解码，记录真实宽高、字节数、SHA256、文件名与场景/物件ID，逐帧核对PNG宽高是否与保存前后videoWidth/videoHeight一致；不一致时记录差异并排查，不标为对应尺寸的原生帧。将视频标识（如BV号）及链接、实际播放/导帧currentTime、登录和实际画质证据、保存前后状态、PNG尺寸和SHA256逐帧绑定，同时记录画面状态、遮挡、视角族和用途。保存原图后可另做明确标注的裁切、联系表或展示缩放；它们不替代原图。

### 10.2 精度和证据边界

- 播放器时间读数不等于容器单帧PTS，不把小数位多当作真实测时精度，也不据截图间隔声称精确状态切换帧。切换只能报告已观察区间及截图前后时间不确定性。
- 经核验的原生解码帧只证明保存的是实测尺寸的视频解码输出（如1920×1080或3840×2160），不能证明上游场景制作/直播渲染原生就是同一分辨率。原生帧中已存在的模糊、压缩、人物、节目文字或心率图层不应偷偷擦除。
- 请求旧参考时刻与实际新currentTime分开。近邻新帧不能冒充旧图同帧；时间、季节、道具布置或动态人物变化必须标明。原生高清不自动增加独立相机基线，缩放、裁切和重复暂停帧不算新增多角度。
- 同一视频可能含不同场景或叙事背景。教室叙事静态背景保持context-only，禁止作为正片硬几何验收约束；其它未证同场、反向视角或来源身份亦分组保留未知。
- 若原生保存不可用、权限或会员档位受限、源视频无更高画质，或切换后实际解码回落，分别记录限制、尝试档位、实际生效档位和真实可得尺寸；不得仅凭菜单存在宣称高码率、2K或4K已生效。可保留明确标为视口截图的备选证据；不能插值放大冒充原生、改标签，或把未取得的目标画质帧写成完成。
- 2026-10-11已实际核验16场45张正式PNG（其中教室叙事背景1张），另有1张独立方法测试帧。此事实支持导帧方法可行，不能推导为45个独立视角、全部视频已看完、跨回放同场确认已完成或任何模型已通过来源验收。

功能验证帧与合格建模参考帧必须分开标记。功能验证只证明导出通路；运动模糊、转场混合、遮挡严重或场景/时刻身份未证实的帧不能因为是原生PNG就成为几何拟合锚点。建模参考须另外核验清晰度、来源身份、实际时刻、布置状态、物件可辨性与有效视角，并记录用途和限制。

### 10.3 接入重建与历史记录

## 11. Git与Issue执行细则（2026-10-11用户最新要求）

- 所有仓库文件修改统一使用正常Git工作树的commit/push，包括模型、图片、脚本与文档，不再使用连接器Git数据API代替后续文件提交。已有历史API生成commit保留，不重写；Issue评论和PR元数据可使用正常GitHub API，因为Git本身不编辑这些内容。
- 每个实际模型/验证/文档阶段留真实当前commit，按版本清晰组织原文件与依赖。先核已有SHA，避免重复、覆盖同名不同内容或将候选混入CURRENT。大文件先核Git限制，需要新LFS费用或权限时单独说明，不能擅自收费或扩权。
- 旧版本的模型、改动、commit和当时图片直接编辑回该版本原评论。保留原有限定、失败试验和紧邻的勘误；不在Issue末尾另堆同版“补录”。确无原条目的历史阶段只建立一次明确版本记录；真正新增日期阶段可独立记录。重复补录评论可改为短迁移指引，保留历史而不永久删除。
